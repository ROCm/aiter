1. 文档用途与结论

用途边界：这份文件记录当前调用关系。public 按 GEMM/BMM 拆分、family module 按 A16W16/A8W8 拆分且底层 exact launcher 复用的方案已经实现；后续 plan/executor ABI 统一仍只是可选设计。
共享的是控制面 A16W16 与 A8W8 都使用 strict 2D opus_gemm 或 batch-first 3D opus_bmm、canonical kernels_list、exact-kid 语义和同一个 JIT module。
A16W16 执行面 production steady-state 走私有 ctypes C ABI；GEMM/BMM adapter 复用 exact launcher，支持 direct 与 Torch-owned workspace 两类计划，并在 family 内为 gfx950 caller-workspace 保留 fast path。
A8W8 执行面 普通 family 的 GEMM/BMM adapter 复用 checked pybind raw entry；只有 MXFP8 BMM 有 Python workspace planner，其 batch-first public contract 通过零拷贝 transpose view 衔接既有 M-major raw ABI，高层 split-1 热路径仍可绕过 public router。

最重要的架构判断：当前是“按 operation 分开的 public contract + 共享 registry/JIT/codegen + family-specific adapter + 复用 exact launcher”。接口职责已经拆清，但 A16 ctypes 与 A8 pybind 等底层 ABI 仍保持各自实现。

5. A16 direct / workspace 两个内部子路径

Direct-output kid

  1. exact plan 判断该 kid 不需要 external workspace。
  2. 若调用者传了 workspace，直接拒绝，避免契约含糊。
  3. C++ 按 Y dtype 进入 direct-output exact table。
  4. kernel 直接写 caller-owned Y。
plan.workspace = None
→ ctypes C ABI
→ opus_a16w16_kid_dispatch<Y dtype>(kid)
→ kernel writes Y
⇄

External-workspace kid

  1. exact instance 声明 workspace dtype，并由 shape/split 推导容量。
  2. 使用 caller workspace，或由 Torch 自动分配。
  3. C++ 进入 workspace exact table；签名与 direct table 不同。
  4. kernel 写 partial；按 exact family 执行 reducer 或对应完成路径。
plan.workspace = (shape, dtype)
→ caller Tensor or torch.empty
→ ctypes C ABI
→ opus_a16w16_workspace_dispatch(kid)
→ partial kernel [+ reduce] → Y
不能把两张 C++ 表直接强行合一：direct 与 workspace launcher 的函数签名不同；workspace dtype 还随 exact kid / arch 变化（当前包含 BF16、FP32）。如果统一，只能在更高层统一抽象，或显式使用可区分的 ABI variant。

gfx950 caller-workspace family fast path

当 route_arch == gfx950、调用者已传 workspace、split_k > 0 且 instance 声明 workspace dtype 时，_launch_a16w16_exact 直接：

  1. 检查 GPU 与 A16 layout；
  2. 调用 cached explicit plan，保留 exact-kid / shape / split 校验；
  3. 跳过通用 family workspace planner 的重复元数据读取；
  4. 直接进入 A16 ctypes raw launch。

这是 A16 family 内部 fast path，不改变 GEMM/BMM 公开语义，最终 C ABI 仍负责 device/stream guard、tensor/workspace 检查与 exact dispatch。

普通 A8 的调用链

upper caller / OPUS tuned row
  → 取得 final kid
  → strict 2D opus_gemm 或 batch-first 3D opus_bmm
  → kernels_list[kid]
  → kernel_tag → logical family

public contract 缓存完成 immutable 路由后，不再在 Python 重复遍历 private family registry；动态 device、shape、stride、runtime arch 和 exact kid 仍由 checked C++ entry 承担。

7. MXFP8 BMM 特殊路径

MXFP8 BMM 的 public 维度与其他 BMM 一样采用 batch-first contract：

XQ: [G, M, K]
WQ: [G, N, K]
Y : [G, M, N]

既有 raw kernel ABI 仍使用 activation/output 的 [M,G,*] M-major view；A8 family adapter 用 transpose(0, 1) 建立零拷贝 view，并显式保留 MXFP8 scale/workspace 语义。

高层 production 分叉

batched_gemm_a8w8_mxscale
  → lookup_mxscale_bmm_config / heuristic
  → cache final global kid + split_k（仅函数与标量，不含 Tensor）
  → 分配 caller-visible Y
      ├─ split_k <= 1
      │    → 对 batch-first tensor 建立 M-major transpose view
      │    → 直接调用 checked raw pybind，绕过 public Python router
      │    → C++ BMM exact table → kernel
      │
      └─ split_k > 1
           → batch-first public opus_bmm
           → _launch_a8w8_mxscale_bmm
           → M-major transpose views
           → cached FP32 workspace plan
           → caller workspace 或 torch.empty
           → checked raw pybind
           → C++ BMM exact table → kernel [+ reduce]
split-1 为什么 bypass shape resolver 已经返回 canonical global kid；直接进入 checked C++ launcher 可避免短 kernel 热路径再次支付 public Python routing 成本。C++ 仍校验 dtype、shape、device、stride、arch 和 exact kid。
split-K 为什么保留 public split-K 需要按 exact kid 计算 effective split 与 FP32 workspace 容量，还要处理 caller-provided / automatic workspace，因此当前复用 public → family planner 链路。

BMM kid 组织

registry 将 8 类 BMM launcher tag 扁平化为同一组 global exact kid，共 45 个：flatmm split-K、fused、minterleave、mouter、mouter tunable、pipeline、wave8n2、wave4m2 selfload。Python 和 C++ 最终均使用 global kid，不在运行时按 local kid 猜测 family。

9. Shared registry / JIT / codegen 架构

OpusGemmInstancekernel metadata
kernels_listcanonical registry

  1. opus_gemm_common.py 中的 kernels_list 是 canonical registry；A16、A8、BMM 的实例最终都合并到这里。
  2. Python public router 读取相同 registry，使用 kernel_tag、arch_prefix、workspace dtype 等 metadata 建立公开契约。
  3. gen_instances.py 根据 registry 与 compiled-kid 集合生成 launcher declaration、manifest、A16 direct/workspace tables、A8 family tables 和 BMM global table。
  4. C++ 在 runtime arch 对应的表中做 exact lookup。未知、未编译或不属于该 arch/family 的 kid 必须报错，不能 fallback。
  5. A16 与 A8 共享 module_deepgemm_opus 构建产物，但 Python 进入该 module 的 binding 方式不同。
单一事实源的含义：新增、删除或改变一个 kid 的 workspace/dtype/arch 语义时，应从 registry metadata 驱动 Python contract 与 codegen；不要再建立一份会漂移的手写 kid 清单。

11. 调整架构时不可破坏的约束

  1. kid 在 public 前确定。CSV、heuristic、fallback 属于 policy；public router 不做策略选择。
  2. exact-kid 不降级。public 与 C++ 均不得换 kid、扫描“相近 kernel”或跨架构 fallback。
  3. kernels_list 保持 canonical。family、arch、workspace dtype 和 codegen 应围绕同一份 instance metadata。
  4. C++ 边界保留动态校验。Python cache 命中不能替代 runtime device、arch、shape、stride、dtype、workspace 与 exact table 检查。
  5. Tensor 生命周期由 Torch 管理。Y 与 workspace 是 Torch Tensor；C++ 只在本次 launch 使用，不长期保存 pointer。
  6. cache 只放 immutable metadata。允许整数、dtype、shape tuple、函数引用和 frozen plan；禁止 Tensor、data pointer、device stream、临时 descriptor。
  7. workspace 契约由 exact kid 决定。不能把 A16 BF16/FP32 typed workspace 和 BMM FP32 workspace 粗暴归为同一种固定 buffer。
  8. direct / workspace ABI 必须可区分。若表或 executor 统一，仍须显式表达不同函数签名和是否需要 reducer。
  9. 保留当前 device / stream 语义。A16 C ABI 安装 device-stream guard；任何 ABI 迁移都要覆盖非 current device 与正确 stream。
  10. Graph replay 不依赖 Python 重走。capture/replay 下不可要求 Python router 在每次 replay 重新建立状态。
  11. BMM shape semantics 不丢失。public 固定 [B,M,K] / [B,N,K] / [B,M,N]；MXFP8 raw M-major view 与 scale layout 必须在 family adapter 中明确存在。
  12. bpreshuffle 是内容契约。不能用普通 layout metadata 校验假装证明 weight 已 preshuffle。

12. 可以调整的位置与影响范围

调整层当前入口适合解决的问题主要风险 / 必测项

开始修改前需要明确的五个决策

  1. 是否进一步统一 plan 对象 / executor ABI？公开接口已经按 GEMM/BMM 职责拆分，底层 exact launcher 已复用。
  2. BMM split-1 高层 bypass 是保留为显式 fast executor，还是让 public 足够快后移除？
  3. A8 是否也迁移 private C ABI；如果迁移，由谁安装 device/stream guard、处理 fake/custom-op 和首次 JIT？
  4. 通用 workspace spec 如何表达 A16 typed/tiled layout、BMM FP32 numel，以及 direct-only / reducer variant？
  5. fast path 是 public 内部实现细节，还是变成 plan/executor 的正式能力位？

workspace_spec 至少应区分：

  • none：direct-only；
  • dtype：BF16 / FP32；

热路径限制：不要在每次调用创建复杂 dataclass、dict 或动态 closure。可以用 frozen/named tuple 表达并按 immutable key 缓存，也可以在 cache miss 产生完整 plan、cache hit 返回紧凑标量 tuple。实际 Tensor 和 stream 始终在调用现场注入。

较安全的演进顺序

  1. 先为现有 A16/A8 行为建立 characterization tests，不改变执行路径。
  2. 引入共同的 scalar plan protocol，让 A16 planner 和 BMM planner 作为两个 backend 实现。
  3. 让现有 opus_gemm/opus_bmm router 消费 plan protocol，但继续调用 A16 ctypes 和 A8 pybind executor。
  4. 分层测量 high-level / public / family raw / C++ kernel，确认 host latency 没有回退。
  5. 最后再单独评估 A8 C ABI 与 BMM bypass 是否值得调整，避免一次改动同时改变 policy、planner 和 binding。

功能与契约
  • 每个 family 的 public 正确性与错误输入拒绝
  • unknown kid、cross-arch kid、uncompiled kid 明确失败
  • A16 direct、caller workspace、automatic workspace
  • A8 noscale、blockscale、gfx942 bpreshuffle
  • BMM split-1、split-K、caller/automatic workspace
  • BF16 / FP32 Y 与 exact workspace dtype
  • 非 current device、正确 stream、多 GPU 边界
  • eager、torch.compile/custom op、Graph capture/replay
性能与生命周期
  • high-level、public、private/raw、kernel 四层分别计时
  • A16 首次 JIT 与 steady-state 分开
  • A16 gfx950 caller-workspace fast path 不回退
  • A8 BMM split-1 bypass 保留或有等价结果
  • cache 中无 Tensor、pointer、stream、descriptor
  • workspace 生命周期完全由 Torch 持有
  • Graph replay 不产生新的 Python routing
  • 短 kernel 重点观察 host overhead，不只看大 shape

完整命令、机器分层和报告格式以 Task1 / Task2 全量测试与性能验证方法 为准。本节只定义架构调整必须覆盖的行为面。
