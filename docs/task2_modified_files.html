1. 最终验收结论

  • gfx950 A16 只把合法 tuned row 的最终 kid 交给 OPUS；tuned miss 保持原有 skinny/PyTorch fallback，不自动进入 OPUS heuristic。gfx950 A8 no-scale kid 2 与 blockscale kid 1 分别进入自己的生成表。
  • A16 依次尝试原始/padded-M tuned 候选，每个候选都在 exact public 前完成 legacy redirect 和 kid/split-K 整体校验；可复用 per-arch heuristic 已抽象到 a16w16_policy.py，但当前 tuned_gemm miss 不调用它。C++ runtime shape/tune lookup 和 C++ heuristic 已删除。
  • 选核、dtype/layout/scale 路由、输出准备、split-K/workspace 和 framework fallback 均由 AITER/Torch 负责；C++ 只保留启动所需安全检查、kid → launcher 查询和 kernel launch。
  • Python public 拆为 strict 2D opus_gemm() 与 batch-first 3D opus_bmm()；A16/A8 family module 提供成对 adapter，继续共享 exact launcher、workspace planner、C++ ABI 和 kernel。MXFP8 仅允许 BMM。
  • checked-in DSV4 BMM CSV 保持 upstream local kernelId=0..653；batched_gemm_op_a8w8.py 只对加载到内存的 OPUS row执行 kid + 8000，最终 exact dispatcher接收 8000..8653。

2. 原本流程与当前流程

Task2 改造前

1. Python wrapper 先查一套 tuned 配置 gemm_op_a16w16.py / common.py::lookup_tuned() 根据 shape 查 CSV；显式 kernelId 或命中 tuned row 时进入旧 tune API。
↓
2. Python miss 后进入 C++ 的另一套策略
Python 命中把 kid/split-K 传给旧 A16/A8 tune entry。
Python 未命中_opus_gemm_bf16_dispatch() → generic C++ opus_gemm()。
↓
3. C++ runtime lookup Generated shape/tune lookup 再按 M/N/K、dtype、bias 等条件查一次；C++ 同时保存一份 runtime policy。
↓
4. C++ per-arch heuristic lookup miss 后进入 gfx942/gfx950/gfx1250 各自的 C++ heuristic，再决定实际 launcher 或 kid。
↓
5. dtype/layout 处理混在 generic 入口 A16 与多种 A8 路径共用或复用 generic/tune 参数，scale 可选，Python、pybind 和 opus_gemm.cu 的合同分散。
↓
6. GPU 执行 C++ 最终选择 launcher 并启动 GPU kernel。选核与 kernel launch 都落在 C++ 路径中。

当前

1. AITER/Torch 完成全部选核
显式 kid直接采用调用时提供的最终 kid。
A16 tuned候选tuned_gemm.py 依次读取原始/padded-M row，校验 kid/split-K，并在 exact public 前完成必要的 gfx942 caller redirect。
A16 tuned miss保持 skinny/PyTorch fallback，不自动运行 OPUS heuristic；显式使用 policy helper 的其他 caller 仍须在 public 前完成 exact 校验。
MXFP8 BMM读取 local kid CSV；仅 OPUS row在内存中执行 +8000，再校验 padded-M 和 fallback heuristic。
OPUS 不可用由上层进入 PyTorch/其他 backend fallback。
↓
2. operation 与最终 kid 进入当前 Python public 逻辑 2D 调用 opus_gemm(XQ, WQ, Y, kid=...)，batch-first 3D 调用 opus_bmm(...)；两者都不查 tuned CSV，也不运行 heuristic，dtype 不决定 GEMM/BMM。
↓
3. Python 整理 dtype/layout kernels_list.get(kid) 取得架构和 kernel 类型；dtype、layout、scale、bias 和 workspace 只做合同校验与参数准备，不重新选 kid。
↓
4. 进入对应私有启动函数
A16W16_launch_a16w16_gemm/bmm() → _launch_a16w16_exact()
A8W8 no-scale_launch_a8w8_gemm/bmm() → _launch_a8w8_exact()
A8W8 blockscale_launch_a8w8_blockscale_gemm/bmm()
A8W8 bpreshuffle_launch_a8w8_blockscale_bpreshuffle_gemm/bmm()
MXFP8 BMM_launch_a8w8_mxscale_bmm()
↓
5. Torch 侧完成 framework 工作 上层准备 Y；A16/MXFP8 需要 Split-K workspace 时由 Torch Tensor 提供；Python 完成 shape、device 和调用参数组织。
↓
6. C++ 只做 kernel + kid dispatch 对应 raw binding 进入分开的 C++ launch API；opus_gemm.cu / opus_bmm.cu 只做启动所需安全检查，并按当前 arch、输出 dtype 和最终 kid 查询 launcher 表，不再执行 shape lookup、heuristic 或 unknown-kid fallback。
↓
7. GPU 执行 Generated launcher 最终检查物理 shape/stride/tile 条件后启动 kernel；Split-K 路径可归约到 Y。
与 Task1 的边界：Task2 在 opus_gemm(kid=...) 或 opus_bmm(kid=...) 前确定最终 exact kid；如果该 kid 是 A16 workspace family，随后由 Task1 的 Torch workspace 流程接管，但不会改变 kid。
