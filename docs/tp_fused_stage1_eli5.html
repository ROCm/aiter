一个 kernel 同时干两件事

把「8 张显卡互相交换数据」和「做矩阵乘法」合并进同一次启动。 它做对了，但没做快。这是它的内部结构。

问题

每张卡只有 1/8 的数据，却都要算全部

8 张 GPU，每张手里 128 个 token。但每张卡都存着全部 384 个专家的权重， 所以每张卡都得为全部 1024 个 token 算一遍。数据必须先互相交换。

这个操作叫 all-gather。以前用 NCCL 做，是一次独立的启动。

想法

启动一次，比启动两次省事

每次「启动」，CPU 都要给 GPU 下一道命令，这道命令本身要花时间。 原来交换和计算是两道命令，那就付两次。合成一道，只付一次。

名词

「小队」是什么

GPU 跑一个 kernel，起来的不是一大团线程，而是一批互相独立的工作组 （workgroup，CUDA 里叫 thread block）。本文里的「小队」就是它。

结构 · 第一步

1024 个小队，抽号分工

1024 个小队的代码完全一样，但需要有人搬数据、有人做准备。 办法是让每队去同一个计数器上加 1，拿走加之前的旧值，那就是它的号码。

ticket64 = atomic_add_agent(a_entry_count, 1)   # 拿走旧值

这个计数器永不清零，所以号码一直往上涨：

为什么绿灯要带轮次号

那个共享变量跨调用不清零。每轮都写 1 的话，第 2 轮的队伍会看到第 1 轮留下的 1 直接冲过去。带上轮次号，第 2 轮等的是 3，旧值骗不了它。清零要 host 介入同步，这么做绕开了。

号码不是 block 编号

每个小队有两个身份。抽到的号码按到达先后分配，决定推送阶段干什么； block 编号是硬件给的固定值，决定计算阶段领哪些块。两者互不相干。

推送阶段用到达顺序，是为了让最早被调度上去的那队当队长，别人等得最短。 计算阶段用固定编号就够了，因为那时候大家已经被绿灯拉齐在同一起跑线。

插播

先说清楚「收件箱」是什么

每张卡都有一块专门用来接收别人数据的内存，叫 rx_x。它是「别人写、我读」的：GPU 3 推给我，写的就是我的 rx_x； 我推给 GPU 3，写的是它的。八张卡互为对方的收件箱。

结构 · 第二步

八个队长互相对暗号

两份余量够不够，取决于没人领先超过一轮。 这件事靠八张卡的队长互相确认。注意是每张卡各有一个队长， 八个队长凑一桌，不是一个总队长。

peer = (tid + rank) % npes                 # 错开起点，八张卡不挤同一个

# ① 告诉 peer：我进第 launch_epoch 轮了
comm_ops.store_i32_system(remote_launch_ready, rank, launch_epoch)

# ② 等 peer 也把他的轮次号写到我这边
mori_shmem.int32_wait_until_greater_than(
    a_launch_ready + peer * 4, launch_epoch - 1)

结构 · 第四步

数到 8 就开工

怎么知道别人的数据都到齐了？一个计数器。每张卡搬完之后加 1， 所有小队都盯着它，数到 8 就往下走。

只等这一次。因为算的时候每一小块都要用到全部 8 张卡的数据， 没有哪一块能提前开工，所以「分块等」只会白白增加开销。

取哪几行？

每块要 32 行。这 32 行的行号存在一张索引表里（sorted_token_ids）， 按表去稠密数据里挑，不需要事先把数据搬来搬去排好。

省下的一步

老做法要先把缩放系数展开成排好序的样子，大约写 4 MB。新的取数方式不用， 直接在片上小内存里现算。

细节

抽号为什么要用到片上暂存区

抽号那条原子加法只能让 1 个线程去做。 256 个线程都去加的话，一口气就消耗 256 个号码，「每队一个号」就变成「每线程一个号」， 角色划分整个乱掉。

可是拿完之后，剩下 255 个线程也得知道这个号——它们要判断自己是不是搬运工、该搬哪几行。 同队内部传一个值，最便宜的办法就是写进暂存区，等一下，大家各自读。

if tid == fx.Int32(0):                      # 只有 0 号线程去抢
    ticket64 = atomic_add_agent(a_entry_count, 1)
    fx.ptr_store(..., ticket_scratch)      # 写进暂存区第 0 个字节
fx.barrier()                              # 等 0 号写完
ticket64 = Vec(ticket_view.load())[0]      # 256 个线程各自读出来

collective_sched.py，emit_ticket_and_roles

同一块暂存区，先后两种用途

覆盖掉没关系，号码早就读进寄存器了。时间上错开，所以不用为抽号单独再申请一块。 暂存区是稀缺资源，每个 CU 上就那么多，占得越少能同时跑的小队越多。

结果

算得完全正确

逐位相同。跟老做法比，输出的每一个字节都一样， 不是「误差很小」，是完全一致。四个规模下都如此。

但更慢

把「合成一次」和「分成两次」放在完全相同的条件下比——同一套矩阵乘法代码、 同样的搬运量、同样的配置，只差启动次数：

合一次每个规模都更慢。省下的那次「下命令」， 还不够抵消 kernel 内部自己做同步的开销。

为什么慢，三个还没验证的猜测：

同步变贵了

分两次的话，两次启动之间天然有一次全系统同步，免费。合一次就得自己在 kernel 里数计数器、自旋等待。

搬运工掉队

32 个搬运队先搬了一趟，回来还要跟别人领一样多的计算块，自然比别人晚收工。

寄存器不够用了

两段代码挤进一个 kernel，每个线程要占的寄存器变多，能同时跑的线程就变少。 这条最好查，读一下编译产物就知道。

下一步

先查第三条。如果查不出也修不掉，那分两次反而是更好的产品形态—— 而分两次的两个零件已经都造好了。

一句话

零件都是好的，装配方式可能选错了

「跨卡直接写显存」这个搬运方式、「按索引表取数」这个取数方式， 都单独验证过是正确且够快的。真正没成立的假设是 「把它们塞进一个 kernel 会更快」。
