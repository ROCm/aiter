1. 两个任务的边界与关系

Task1：workspace 所有权迁移 把 A16W16 Split-K workspace 从 C++ 的进程级/per-stream 管理迁移为调用级 Torch Tensor。 Python 根据最终 kid 规划 shape、dtype 和 split-K；调用方可以复用 Tensor，未提供时由当前调用创建。
Task2：public operation 与启动边界收敛 tuned 候选校验、可选 policy helper、fallback 和输出准备归 AITER/Torch；公开入口按逻辑 rank 拆为 strict 2D opus_gemm(..., kid=...) 与 batch-first 3D opus_bmm(..., kid=...)。C++ launcher/kernel 继续复用，只校验物理合同并执行 exact kid → launcher。
依赖关系：Task2 必须先解析出最终 kid，Task1 才能按该 kid 的真实 metadata 规划 workspace。两项开发在历史提交中交错推进，但最终运行顺序固定为“选出 final kid → 规划 workspace → exact launch”。
问题Task1 负责Task2 负责
谁决定运行哪个 kernel？不重新选核；消费最终 kid。上层 caller 处理 tuned/fallback；若某调用方显式采用 heuristic，也必须在 public 前完成。public 只接收 final kid。
谁拥有 workspace？Torch/caller，生命周期限制在当前调用或调用方。只把 workspace 参数路由到需要它的 family。
C++ 做什么？接收 direct pointer，检查 dtype、容量、对齐和设备。按 arch、family、Y dtype 和 exact kid 查询 typed table，不执行运行时策略。
失败如何处理？不合法 workspace 在启动前明确报错，不隐藏分配或替换 kid。exact public 不 fallback；只有进入 public 之前的高层 caller 可以选择其他 backend。

2. 最终运行链路与任务交接点

1. 高层 caller显式 kid 或合法 tuned row；当前 tuned miss 保持 skinny/PyTorch fallback。
2. operation + final kid2D 进入 opus_gemm，batch-first 3D 进入 opus_bmm。
3. canonical routekernels_list.get(kid) 确定 arch/family。
4. family 合同检查 dtype、layout、scale、bias、shape。
5. workspace plan按 exact metadata 复用或创建 Torch Tensor。
6. C++ exact tabledirect pointer + kid → 唯一 launcher。
7. GPU / reducemain 写 caller workspace，reducer 写 Y；direct kid 直接写 Y。

关键不变量：public 路径不会根据数值区间猜 family，不会把一个 kid 重定向为另一个 kid，也不会在 C++ 内分配或缓存 workspace。

4. 可复用的逻辑修改流程

4.1 Task1：workspace To Torch

  1. 盘点 exact-kid 物理合同。从 canonical registry 提取每个架构的 tile、split-K、workspace dtype、输出 dtype、bias 和 batch 限制。
  2. 建立纯标量 workspace plan。先解析最终 kid，再计算 allocation split、shape、numel、dtype；cache 不保存 Tensor、指针、device、stream。
  3. 拆分 typed dispatch table。codegen 生成 direct/workspace/fused 表和输入检查，空 family 生成显式空表。
  4. 迁移 C++/GPU ABI。launcher、main kernel 和 reducer 接收 direct pointer；删除内部 allocator、per-stream registry 和 workspace-init 依赖。
  5. 接入 Torch 生命周期。caller workspace 先严格校验；否则当前调用执行 torch.empty。Graph 使用 graph-private pool，双 stream 各持有自己的 Tensor。
  6. 验证正反合同。数值、BF16/FP32 storage、容量差一、非连续、错误 dtype/device/alignment、non-workspace kid、Graph 和并发全部覆盖。

4.2 Task2：选核归 AITER/Torch，C++ exact dispatch

  1. 冻结 canonical id 空间。保留架构 id 段和唯一 merged registry；新 family 使用不冲突的全局 id。
  2. 把策略移到 caller。高层 A16 caller 校验 tuned CSV 候选并整体丢弃无效 kid/split-K；当前 tuned_gemm miss 后保持 skinny/PyTorch fallback，不自动进入 OPUS heuristic。可复用 heuristic 只作为显式 caller policy helper。
  3. 按 operation 收敛 public surface。导出 strict 2D opus_gemm(XQ, WQ, Y, *, kid, ...) 与 batch-first 3D opus_bmm(...)，都要求 caller-owned Y 和 mandatory final kid。
  4. 按 family 固定合同。A16、A8 no-scale、blockscale、bpreshuffle、MXFP8 BMM 各自检查 dtype/layout/scale/workspace，不通过数字区间猜路由。
  5. 删除 C++ runtime policy。移除 shape/tuned lookup 和 per-arch heuristic headers；C++ 仅做安全检查与 exact table lookup。
  6. 迁移生产 caller 与 tuner。所有调用方先创建 Y、解析 final kid，再按逻辑 rank 进入 GEMM 或 BMM public；subset build 保证合法 tuned/显式 policy 所需 kid 可编译。
  7. 验证路由与兼容性。覆盖 explicit/tuned/miss/invalid/fallback、跨架构拒绝、Graph、stream、ABI、all-kid correctness 和分层性能。

6. Reviewer 快速检查清单

  • Task1 的结论只涉及 workspace 所有权、类型、生命周期与 direct pointer，不把 Task2 的选核迁移算作 Task1。
  • Task2 的 opus_gemm/opus_bmm 接收的是 final kid；tuned/heuristic/fallback 不出现在 public 或 C++ exact launch 内。
  • GEMM/BMM 由逻辑 rank 和所选 public 决定，不由 dtype 决定；family module 复用同一 exact launcher 与 workspace planner。
  • 显式 kid 不被静默改写；不支持的 dtype/layout/workspace 直接失败。
  • 任何 cache、global registry 或 C++ 对象都不持有调用方 Tensor/data pointer。
  • 文件变化细节分别查看 Task1 与 Task2 页面；完整验收按 验证方法执行。
  • 测试报告必须绑定 git SHA、目标 GPU、JIT module SHA-256 和日志；skip、NOT RUN、BLOCKED 不得写成 PASS。
