# Pre-compiled gfx1250 kernels (`.co`)

Device code for the three 4-wave kid families, built ahead of time instead of by
the aiter JIT:

| family | pipeline | entries | tiles |
|---|---|--:|---|
| `a16w16_4wave_co` | [`..._4wave_compute_...cuh`](../include/gfx1250/opus_gemm_pipeline_a16w16_4wave_compute_gfx1250.cuh) | 64 | `B_M = 128`, `B_K = 128` only, `B_N` 64/128/192/256 |
| `a16w16_4wave_wl_co` | [`..._4wave_wl_...cuh`](../include/gfx1250/opus_gemm_pipeline_a16w16_4wave_wl_gfx1250.cuh) | 155 | `B_M` 32/64/96/128 x the same `B_N`, via `wave_layout`; `B_K` 128 and 256 |
| `a16w16_4wave_wlr_co` | [`..._4wave_wlr_...cuh`](../include/gfx1250/opus_gemm_pipeline_a16w16_4wave_wlr_gfx1250.cuh) | 2 | `256x256x64`, P=4, pinned A and ring C staging |

They differ in one thing: the `wl` pipeline takes the wave layout
(`TileM x TileN`, product 4) as a parameter, so it reaches `B_M` below 128 —
`B_M = kExpM * 16 * TileM`. The compute family is fixed-layout, which makes its
tile set a strict subset of the `wl` one. That matters when a shape cannot fill
the machine: at `M = 512, N = 2048` a `128x64` tile yields 128 workgroups on
256 CUs while a `64x64` tile yields 256.

Neither family supports split-K, which is what bounds where they win: a shape
whose tuned winner wants `splitK >= 2` goes to the JIT `_ws` families instead,
and adding a `.co` entry for its tile will not take it back.

## Why

The symmetric 4-wave compute pipeline needs three things a release ROCm
toolchain does not have:

| Requirement | Stock ROCm |
|---|---|
| `amdgpu_pin_vgpr` automatic locals (named-register lowering) | not available |
| `amdgpu_num_vgpr(1024)` / v256–v1023 | not available |
| `-mllvm -amdgpu-expert-scheduling-mode` | rejected |

The last one is the dangerous one: `hip_flag_checker` in
[`aiter/jit/core.py`](../../../aiter/jit/core.py) **silently drops** flags the
compiler rejects, so a JIT build would not fail — it would quietly produce a
differently-scheduled kernel. Hence the offline path.

Only the device kernel is bypassed. The host launcher, manifest, tune lookup,
dispatch and tuned-CSV schema are all generated by the ordinary codegen, so
moving this family back to JIT later is a branch in
`codegen/gen_instances_gfx1250.py` and nothing else.

## Named-register pinning

The current regular and A0 images are rebuilt with
[`amdgpu-pin-hybrid`](https://github.com/yuyzhang512/llvm-project/commits/amdgpu-pin-hybrid/)
commit `352c37bad3561fc0f23163d5b1419910213d26bb`. Its automatic-local pin attributes
remain compatible with the earlier named-register implementation:

```cpp
__attribute__((amdgpu_pin_vgpr(Base))) opus::vector_t<float, 8> slot = value;
```

Unlike the old `__builtin_amdgcn_pin_vgpr(value, Base)` value hint, each read and
write of this local lowers to `llvm.read_register` / `llvm.write_register` for
`v[Base:Base+7]`. A pinned local has **no address**. Attributes on struct members,
reference captures of an external pinned local, and whole-tile vectors are not
substitutes for pinning legal WMMA fragment tuples.

[`opus_named_vgpr_bank_gfx1250.cuh`](../include/gfx1250/opus_named_vgpr_bank_gfx1250.cuh)
uses one ordinary SSA-backed member per fragment. `set<I>()` declares a new
attribute-bearing local, writes the fragment into its physical tuple, and
immediately copies it out to the member; `get<I>()` returns that SSA value.
This is deliberate: a getter that re-reads the physical tuple makes loop blocks
read-before-write, causing `scanNamedRegs` to reserve the tuple and preventing
WMMA's destructive-update destination from coalescing into it. It produced
low-WMMA/high-C copies and a severe measured regression. The write/copy-out form
restores direct named-bank WMMA destinations with the same LLVM HEAD.

The SSA member is **not** itself an attributed, whole-lifetime physical variable;
therefore the builder validates actual producer placement in the ELF ISA rather
than assuming it. Accumulators are explicitly zeroed before the prologue; B
(and the wlr A bank) are loaded before use. Keeping the pinned local inside
`set()` also avoids the generic-lambda reference-capture restriction.

The original tuple bases/strides, kids, symbols and 64-byte kernarg are retained
for the compute, wl and wlr families. Named registers are real physical aliases,
not a promise that an overlapping/unavailable request will safely fall back.
The wlr `OPUS_PIN_A=1` + `OPUS_C_BF16F32=1` combination is rejected because its
experimental A and C banks share a base. `OPUS_NO_PIN=1` remains an explicit
control using real unpinned C++ storage, not the old builtin. Use integer-literal
pin-control defines; the builder rejects expressions it cannot verify.

Every build checks the optimized device IR for **both reads and writes of every
expected accumulator/B/A tuple**, and checks that **every WMMA destination in
the actual ELF** is in its named accumulator/output bank. It fails on ignored
attributes or a kernarg-size mismatch, and records that evidence plus the ELF SHA256 in
`build_info.json`. A compiler merely accepting an attribute name is not enough.
The recommended LLVM HEAD includes the fixes for generic-lambda dependent
register numbers, deduced `auto`, and loop accumulator propagation.

Current hybrid/strict build and runtime validation details are in
[HYBRID_VALIDATION.md](HYBRID_VALIDATION.md). The earlier std-branch experiment
is retained as historical context in [NAMED_REG_VALIDATION.md](NAMED_REG_VALIDATION.md).

## Layout

```
gen_co/
├── co_kernels.json        # THE source of truth (see below)
├── build_co.py            # the producer
└── gfx1250/
    ├── <launcher_name>.co  # bare amdhsa ELF, one kernel each   (tracked)
    ├── build_info.json     # compiler + flags + per-kernel metrics (tracked)
    └── asm/                # debug listings, .gitignored
        ├── <launcher_name>.ll   # optimized device IR / named tuples
        ├── <launcher_name>.s    # compiler -S output
        └── <launcher_name>.dis  # llvm-objdump of the .co itself
```

`<launcher_name>` is the same string three times over — the `.co` filename, the
`extern "C"` kernel symbol inside it, and the host launcher symbol — because all
three are derived from `OpusGemmInstance.name` in
[`opus_gemm_common.py`](../opus_gemm_common.py). Nothing has to be kept in sync
by hand, and there is no sidecar mapping file.

`.co` files are packaged automatically: `setup.py`'s `prepare_packaging()` copies
all of `csrc/`, and `MANIFEST.in`'s `global-exclude` only drops `*.py[cod]`. The
same function recursively deletes `gen_co/**/asm/` from the copy — being `.gitignored` does
nothing for a filesystem copy, so otherwise every wheel built in a tree that had
run `build_co.py` would carry a few MB of listings.

## `co_kernels.json`

One entry per pre-compiled variant, read by BOTH `opus_gemm_common.py` (which
turns it into the kid table the JIT codegen consumes) and `build_co.py`. Adding
a variant — another VGPR budget, another cluster shape, other device flags — is
an edit to this file and nothing else.

| field | notes |
|---|---|
| `kid` | explicit, not positional; reordering the list must not renumber. IDs are local to the `a16w16/gfx1250/CU` namespace, not a global numeric band |
| `tag` | `kernel_tag`: `a16w16_4wave_co`, `a16w16_4wave_wl_co` or `a16w16_4wave_wlr_co`; picks the codegen emit branch and the traits/kargs names |
| `block_size` | threads per workgroup; **must** equal `launch_bounds[0]` (asserted) |
| `tile` | `[B_M, B_N, B_K]` |
| `num_slots` | LDS prefetch ring depth P: compute/wl entries use 3; the wlr entries use 4 |
| `wave_layout` | `[TileM, TileN]`, product 4. **`wl` and `wlr` entries** — it is what lets that
family express `B_M` other than 128, since `B_M = kExpM * 16 * TileM`. Lands in the symbol
name as `_w{m}x{n}`. |
| `cluster` | `[m, n]` → `__cluster_dims__(m, n, 1)` |
| `launch_bounds` | `[maxThreadsPerBlock, minWavesPerEU]` |
| `num_vgpr` | `amdgpu_num_vgpr(N)`; `0` omits the attribute |
| `dtypes` | `a`/`b`/`c`/`acc`; `c` is the launcher's only `output_dtype` |
| `device_flags` | extra device-pass flags for this entry; the standalone strict build also records `-nogpulib` |
| `variant` | optional name suffix, for two entries differing ONLY in `device_flags` |

`wave_layout`, `num_vgpr`, `launch_bounds[1]` and `cluster` all land in the symbol
name (`...[_w{m}x{n}]_c{m}x{n}_p{slots}_v{vgpr}w{waves}[_{variant}]`), so no two
entries can collide on one `.co`.

### Which tiles are worth adding

Two numbers decide it, and both are arithmetic on the entry — no build required.

**Grid.** With no split-K to widen it, `⌈M/B_M⌉ * ⌈N/B_N⌉` is all the parallelism
a shape gets, and it has to reach the CU count. A tile that leaves the machine
half idle loses to a `_ws` kid that splits K instead, however good its inner loop
is.

**WMMA budget.** A K step has
`(B_K/64) * kNumNSub * kExpM * kExpNPerSub * kExpKHalf` WMMAs, and this pipeline
hides its ds_reads, its barrier handshake and its TDM issue in the gaps between
them. Measured over the 84-shape DSV4 sweep, every entry that wins a shape has at
least **16**; a tile with 8 was added as a probe and won none of the five shapes
it was aimed at. Below 16, expect nothing.

The two pull against each other — shrinking `B_M`/`B_N` to raise the grid lowers
the budget — which is why the useful additions are the ones that raise `B_K`
instead: `B_K = 256` doubles the budget at no cost to the grid. That is what the
`64x64x256` and `32x64x256` entries are, and they took 8 shapes off the `_ws`
families when they were added. The loader asserts that, and asserts each `kid` is in band.

A **missing** `co_kernels.json` leaves the family empty rather than breaking the
build — a data file that failed to ship should cost the co kids, not all of opus.
An entry whose **`.co` is not on disk** degrades the same way: `_load_co_kernels`
drops that kid (with a warning on stderr) so it can never reach the codegen, the
tuner or a tuned CSV and then fail at its first launch. `build_co.py` is the one
consumer that reads the unfiltered table (`gfx1250_4wave_co_kernels_declared`) —
it is what creates the missing files.

## Rebuilding

Needs an LLVM that has named-register `amdgpu_pin_vgpr` locals, `amdgpu_num_vgpr` and the
gfx1250 register file. **No specific version is assumed or checked** — the point
is that you can swap toolchains freely:

```sh
python3 csrc/opus_gemm/gen_co/build_co.py --llvm-bin /path/to/llvm/build/bin
# or: OPUS_CO_LLVM_BIN=... python3 csrc/opus_gemm/gen_co/build_co.py
```

`--device-flag` appends a flag to **every** entry, on top of that entry's own
`device_flags`, for investigations that need the whole family built one way.
`-DOPUS_CO_NO_1WG_PAD` is the one that exists today: it drops the LDS pad that
holds the affected variants at 1 WG/CU. `_expected_lds` follows the flag, so the
`group_segment_fixed_size` check still passes rather than failing the build.
Whatever was used is recorded per entry in `build_info.json`, so an artifact
never hides which flags produced it.

`HIP_CLANG_PATH` is how hipcc is pointed at another clang, so the driver flags
stay identical whichever toolchain is selected. `llvm-readelf` and
`llvm-objdump` are taken from the same `--llvm-bin`, so the metadata reader and
the disassembler always match the compiler.

The following artifact checks are fatal:

* bare ELF64/AMDGPU processor identity matches the real regular/strict target;
* no unresolved device symbols;
* exactly one kernel, named as expected — the three-way name identity above;
* `group_segment_fixed_size` equals the traits' `kLdsTotalBytes`;
* `kernarg_segment_size` is exactly 64 bytes, matching the host ABI;
* every expected pinned fragment has named-register reads and writes in device
  IR (except an explicitly requested `OPUS_NO_PIN` control);
* every WMMA producer destination in the actual CO is in the named accumulator
  or bf16-output bank, not a low-register temporary copied there afterwards.

Everything else is recorded, not judged. Spills only fail the build under
`--fail-on-spill`: at the tighter VGPR budgets they are the expected outcome, not
a malfunction. `build_info.json` carries the resolved clang and its version, each
entry's exact flags, VGPR/SGPR/spill/LDS/kernarg, and four numbers scraped from
the assembly — `lines`, `va_vdst0`, `wmma`, `wmma_dst_hi` (both `asm_*` from the
`-S` listing and `dis_*` from the disassembly).

Those last two are how you tell whether a new toolchain still honours the pin.
The reference for the 1024-VGPR entry is **`va_vdst0` = 21 and `wmma_dst_hi` =
768 of 768**; an unpinned build of the same kernel gives 160 and 0 of 768. There
is deliberately no threshold on VGPR count any more — with several budgets in
the table there is no single number that means "the pin worked".

## Regular and A0 strict roots

All 221 regular images under `gfx1250/` are rebuilt with the hybrid compiler.
`named_reg/gfx1250/` mirrors the same regular images for compatibility with the
previous explicit-candidate path. The additional 221 A0 images are separate:

| runtime image root | compiler target | ELF processor |
|---|---|---|
| `gen_co/` or `gen_co/named_reg/` | `gfx1250` | `0x49` |
| `gen_co/gfx1250-a0/` | `gfx1250-strict` | `0xeb` |

The runtime architecture remains `gfx1250`; strict is a distinct compiler CPU,
not a runtime architecture name or a relabelled regular object. Both profiles retain
exactly the same manifest kids, symbols and 64-byte ABI.

The default loader now selects per **current HIP device** using its ASIC
Revision (the same HSA field printed by `rocminfo`, not PCI/chip revision):
`0x0` selects `gen_co/gfx1250-a0/`; `0x1` and later select
`gen_co/gfx1250/`. No stepping-specific kid or manual environment setting is
needed. The lookup uses HIP device ordinals, so visibility remapping and mixed
A0/B0 nodes do not use a node-wide minimum.

`OPUS_GEN_CO_DIR` can name a combined root containing `gfx1250-a0/` and
`gfx1250/`, or a direct profile leaf such as `gen_co/gfx1250-a0/`. A direct leaf
is read without adding another subdirectory, but its ELF processor must match the detected
stepping. Missing/wrong A0 images fail clearly rather than falling back to B0.

```sh
# Default automatic selection; do not set a stepping-specific root.
python3 -m pytest -q op_tests/test_opus_co_integration.py

# Optional explicit combined root; selection remains device-aware:
export OPUS_GEN_CO_DIR="$PWD/csrc/opus_gemm/gen_co"

# Rebuild A0 separately; the default output is gen_co/gfx1250-a0/:
python3 csrc/opus_gemm/gen_co/build_co.py --llvm-bin /path/to/hybrid/bin \
    --offload-arch=gfx1250-strict --fail-on-spill
```

On c7-1, HIP `7.16.26385` / ROCm 10.1 successfully loads the private strict ELF;
HIP `7.15.26333` / ROCm 10.0 returns `hipErrorNoBinaryForGpu`. Do not change its
processor flag to work around an old runtime. The strict BF16 kernels are
standalone and use `-nogpulib` because older SDKs lack strict ISA bitcode; every
CO is checked for unresolved device symbols. The unsigned TDM descriptor
prototype is selected with C++17 SFINAE and equal-width bit casts.

Registrations are cached by **HIP device + resolved absolute image path**,
with a thread-local hot path keyed by symbol/device/root. The same kid can be
used on A0 and B0 devices in one process, and a changed root is re-resolved;
failed registrations are rolled back rather than falling back to an old entry.
The generated launcher no longer holds the first kernel in a function-local
static. Its current device must match the input tensor device, and callers must
supply that device's stream (normal Python entry points already do this).

Keep environment changes out of concurrent launches. Same-path file rewrites,
symlink retargeting and device/context resets do not invalidate loaded modules;
use a fresh process for those changes. Captured graphs retain the function they
captured, so switching a root does not retarget an existing graph. Old modules
remain alive rather than being evicted while a graph or launch may still use them.
Use an explicit `--out-dir` to intentionally rebuild a production root. Nested
candidate/A0 `asm/` directories are excluded from wheels as well.

## Runtime

[`opus_co_launch_gfx1250.cuh`](../include/gfx1250/opus_co_launch_gfx1250.cuh)
selects `$OPUS_GEN_CO_DIR/gfx1250-a0/<name>.co` for current-device ASIC
Revision 0, or `$OPUS_GEN_CO_DIR/gfx1250/<name>.co` for Revision 1 and later
(direct-profile overrides are validated too). It registers once per device and
resolved path, then launches via `AiterAsmKernelFast` + `hipDrvLaunchKernelEx`.

`OPUS_GEN_CO_DIR` is exported by `import aiter` (`aiter/jit/core.py`, right next
to `AITER_ASM_DIR`) and can be overridden in the environment to swap in a freshly
built `.co` without rebuilding the module. `module_deepgemm_opus` also bakes it as
a compile-time macro, but only as a fallback for builds that do not go through
aiter's Python entry points: for a **prebuilt wheel** the macro holds the build
tree's `aiter_meta/` path, which `setup.py` deletes when it is done — the
import-time value is the only one that knows where the files ended up.

Cluster launch needs `-DAITER_ENABLE_CLUSTER_LAUNCH` (ROCm >= 7.0); without it
`AiterAsmKernelFast` refuses a clustered launch rather than silently dropping the
cluster dims. `core.py` defines it whenever `gfx1250` appears in `GPU_ARCHS` (not
just when it is the arch `get_gfx()` happens to pick), so a multi-arch build
cannot produce `.co` kids it will then reject at launch.

The kernels are compiled with `-D__HIPCC_RTC__`, which strips HIP's implicit
runtime wrapper. That is what leaves them with a single 64-byte by-value kernarg
and **no hidden/implicit args** — the same shape as the hand-written asm `.co`
files aiter already loads this way, so `HIP_LAUNCH_PARAM_BUFFER_POINTER` needs
nothing appended.

The struct behind that kernarg
([`opus_gemm_4wave_compute_kargs_gfx1250`](../include/gfx1250/opus_gemm_traits_a16w16_gfx1250.cuh))
is `static_assert`ed at exactly 64 bytes, and `build_info.json` records
`kernarg_segment_size` — so "still 64" after a rebuild is the signal that the
ABI baked into the shipped `.co` has not drifted from the header the host
compiles against.

## Dispatch

All three tags share this path. These kids get **their own pair of tables** in
[`opus_gemm_arch_gfx1250.cuh`](../include/gfx1250/opus_gemm_arch_gfx1250.cuh) —
`opus_a16w16_co_tune_dispatch_gfx1250(kid)` for the explicit-`kernelId` / tuner
path and `opus_a16w16_co_dispatch_gfx1250(M, N, K)` for tuned-CSV production —
because the family takes no workspace and so its launchers do not fit the entry
type the split-K kids share. `opus_gemm()` consults the `(M, N, K)` one first: a
hit skips the `hipMalloc` / `hipDeviceSynchronize` / `hipFree` that every split-K
kid needs. Bias and non-bf16 `Y` fall through to split-K, since this pipeline has
neither an epilogue nor a reduce kernel to serve them.

The shape heuristic never returns a `.co` kid; reaching one always means a tuned
CSV row or an explicit `kernelId`. On the tuning side all three tags are answered
early by `kid_rejects_shape` — no buffer resource, every tail clamped by the D#,
so no M/N/K alignment applies. Naming only one of them there once cost the `wl`
family every shape whose `N` fell outside an unrelated gfx942 whitelist; see
issue 4 in [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md).
