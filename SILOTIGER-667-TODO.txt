=== FlyDSL FP8-down block2d scaled-convert fold track (aiter kernel work; surfaced by the g9 caveat) ===
This track attacks the FP8-down block2d(128,128) cost that the g9_compare.md header flags as a
CK-favored lower bound ("block2d(128,128) costs FlyDSL ~10-38% vs pertensor (B1)"). The cost is
NOT weight-byte traffic (FP8-down fly_%peak is still ~66-74%); it is LATENCY: in the block2d branch
of build_down_reduce_fp8 (aiter/ops/flydsl/kernels/warp_decode_moe.py, the `if const_expr(block2d)`
path) the dot2 chain is drained PER 128-wide K-block so the per-block f32 scale can be folded after
the dot (`acc[h] += dot_i * (rw * ds_i)`), plus an extra scale buffer_load + address compute per
block -- vs the pertensor path which loads one broadcast scale and drains the whole K-range ONCE.
Fragmenting the dot2 ILP + the per-block drains is what hurts, worst at B=1 (the 38% end); it washes
out by B=32 (bandwidth-bound, FP8-down ratios already ~0.95-1.00). This is an implementation artifact,
not intrinsic to block scaling, so it is recoverable WITHOUT dropping to coarser pertensor scales
(which would be a model-accuracy decision, not a kernel win). Est ~1-1.5 days for the fold; +0.5-1 d
if the independent-partials variant is also needed. Anchor = the identity-scale convert today:
`fp8x2_to_bf16x2(dw[h][w_word], one_f32, hi=w_hi)` feeds a post-dot multiply by ds_i.
    Sub-steps:
    - Fold the per-block exponent into the scaled FP8->BF16 convert instead of the post-dot
      multiply: pass the block scale into v_cvt_scalef32_pk_bf16_fp8 (currently run with one_f32)
      so no separate per-block multiply is needed and the dot chain need not break to fold it.
      block scale is exponent-only, so this is a cheap swap of the convert's scale operand keyed on
      col_blk = k_base // scale_bk. Est ~1 d.
    - If the convert-fold alone does not restore ILP, keep independent per-K-block f32 partials in
      flight (extend the G7 dot2_acc idea ACROSS block boundaries) and fold each block's scale at the
      very end, rather than draining inside each block. Est ~0.5-1 d.
    - Correctness gate: reuse the existing block2d unit tests (h*_block2d / down_*_block2d cases in
      op_tests/flydsl_tests/test_flydsl_warp_decode_moe.py) at cos>=0.999; block2d output must be
      bit-comparable to the current fold (exponent-only scale is associative-safe here).
    - Perf-confirm at B=1/2 (the latency regime where the 10-38% lives) that FP8-down closes toward
      the pertensor number while keeping block2d(128,128); B>=8 is expected near-neutral (already at
      the memory wall). Re-run the G9 compare so the FP8-down cells reflect the recovered path.
    - GENERALIZED FORM -- offline weight prepack + versioned layout contract (K3-report technique).
      The deeper form of "cut runtime dequant work"
      is to permute/pre-interleave the packed FP8/FP4 weights OFFLINE (at model-load) so nibbles/
      bytes arrive in the order the packed convert + lane mapping want, and to co-locate the e8m0/
      f32 microscale with the block it covers -- removing shift/mask/shuffle from the inner loop
      entirely (superset of the in-kernel convert-fold above). Needs a DECLARED, VERSIONED prepack
      layout contract (not the implicit expert-major weight-tensor assumption). Cheapest to introduce
      alongside the FP4 gate_up prepack (track 2's OPTIONAL bullet) rather than retrofit; applies to
      both the FlyDSL and CK paths. Est ~1-2 d + a layout-contract decision.
    Cross-refs: g9_compare.md config-policy header ("FP8-down ratio is a CK-favored lower bound:
    block2d(128,128) costs FlyDSL ~10-38% vs pertensor (B1)"); SILOTIGER-667.md comment "Notes from
    the publicly released K3 technical report" (offline weight permutation + push dequant into the
    packed scaled-convert -- "the difference between a regression and a win"); track 2 OPTIONAL
    prepack bullet. (The ~10-38% down block2d-vs-pertensor cost was an A/B measurement at iters=1000,
    worst at minimax B=1; gate_up was neutral.)

=== Activation-input datatypes track: plain FP8 + MXFP8 activations (aiter kernel work) ===
This track fills the remaining ACTIVATION-side datatype targets. The ticket's "Datatypes targeted"
lists activations = BF16 (decode default, done) AND FP8; Kimi-K3 additionally needs MXFP8 (block-
scaled) activations. Both warp-decode kernels currently take BF16 activations; the only FP8-act peer
so far is B4's block-scaled gate_up (build_gate_up_fp8_act_module / flydsl_warp_decode_gate_up_fp8act:
FP8 e4m3 x + Block2D<1,128> act scale, both operands scaled-converted to BF16, scale folded after
dot2). That is the scaffold; two variants remain:
  (a) PLAIN FP8 activation (per-tensor / per-token) with the input-side BF16->FP8 quant FUSED into
      gate_up, so callers pass bf16 x and the kernel quantizes on the way in.
  (b) MXFP8 (block-scaled) activation -- e8m0 microscale on x, the activation-side mirror of the
      MXFP4 weight path (power-of-two -> applied IN the convert, exact). Distinct from (a); required
      for a faithful Kimi-K3 (track 8).
Est ~1 d for (a), ~1-1.5 d for (b).
    Sub-steps:
    - (a) Add a per-tensor/per-token x_scale path to gate_up (fold after dot2, scale=1 in the
      convert per the exponent-only E8M0 rule); optionally fuse a BF16->FP8 x quant prologue so the
      entry point accepts bf16 x. Est ~1 d.
    - (b) Add an e8m0 (model-block, e.g. 1x128) x microscale applied in-convert like the FP4 weight
      scale (reuse e8m0_byte_to_f32); mirror build_gate_up_fp8_act_module. Est ~1-1.5 d.
    - Correctness: extend the dequant-both torch ref (_ref_gate_up_fp8act_pool) to each variant,
      cos>=0.99; add op_test cases at small + real E (256/512).
    - LOWER PRIORITY: FP8/MXFP8 on the down INTERMEDIATE (bf16 today). Decode intermediate is tiny,
      so only relevant for a fully-quantized 2-stage pipeline; defer unless a use-case appears.
    Cross-refs: SILOTIGER-667.md "Datatypes targeted" (FP8 act; MXFP8 for K3); the E8M0 convert rule
    in the header above; the existing FP8-act scaffold flydsl_warp_decode_gate_up_fp8act.

=== Occupancy / L2-locality perf levers track (OPEN RESEARCH; so-far no-win) ===
The residual perf-research corner. TWO occupancy levers are already CLOSED as decode no-wins (see the
header): split-K (G5, archived) and LDS n_waves cooperative caching (G6). The items below share the
same physics -- B=1 warp-decode is launch/memory-latency-floor bound (~4-5 us fixed floor), one wave
per output scalar with almost no cross-wave reuse (~1.1x expected at ref shapes) -- so they are
LIKELY no-wins too. Kept for provenance; pursue only if a regime with real cross-wave reuse appears.
    Items:
    - XCD swizzle re-test on small-grid Qwen (INTER=512, B=1). The GEMM-decode work found XCD/chiplet
      workgroup remap a LARGE win at small N (M=1/N=2048: 7.59 TB/s = 95% HBM vs 4.09 = 51%), but the
      MoE warp-decode sweeps found it neutral/REGRESSING. The ticket flags this as a genuine GEMM-vs-
      MoE conflict -- "regime-limited, not refuted" -- because the small-grid MoE case (Qwen INTER=512
      B=1) was never isolated. GATED on a cross-wave reuse tiling existing first (next item).
    - Cross-wave reuse tiling (the PREREQUISITE for the XCD re-test). MoE warp-decode has no register
      tile, so XCD remap has nothing to co-locate in L2. Would need a tokenbatched kMPerWarp / LDS
      activation staging that CREATES cross-wave reuse. CAVEAT: the ticket's "Tried and dropped"
      already records weight-reuse register tile as "not feasible at decode (reuse ceiling ~1.1x)",
      so this is open research, likely low-value. (Note: designed & implemented for the sibling
      GEMM-decode kernels in gemm_decode_design.md -- Axis 3 GrpsShrB / A4 kMPerWarp / B1/B2 -- but
      NOT for MoE warp-decode.)
    - Lane-teams over disjoint expert subsets (K3-report technique). Subdivide wave64 into T teams of
      64/T lanes, each team taking TOPK/T experts, shortening the serial TOPK loop by T; the butterfly
      reduce yields the cross-team sum for free and router_wt is already folded per expert. Same
      "increase parallelism" lever as split-K -> most likely to pay only in the small-grid occupancy-
      bound regime, NOT at the HBM wall. Tightens the vectorized-load divisibility constraint
      (lanes-per-team * kVector | INTER) and makes expert id + scale metadata non-wave-uniform.
      Closest existing knob is kLanesPerOutput (subdivides the reduction axis, not the expert axis).
    Cross-refs: SILOTIGER-667.md "XCD swizzle: conflicting GEMM-vs-MoE data" + "Remaining/untried" #4
    + the lane-teams note in the ticket's K3-report comment; gemm_decode_design.md (cross-wave reuse
    for the sibling GEMM-decode kernels). G5 split-K live impl archived on
    samaario/warp-decode-moe-splitk-attic (see the CLOSED no-wins note in the header).
