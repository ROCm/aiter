=== CK FP4 gate_up fast path track (upstream CK kernel work; surfaced by D7) ===
This track builds the missing fast packed-FP4 gate_up path in CK. It is UPSTREAM CK work
(rocm-libraries branch users/samremes/ck/warp-decode, commit 62e30c9098), not aiter, so it
needs a CK build + a PR to that branch -- distinct from this ticket's harness. Motivation:
the ticket's own #1 remaining item ("FP4 gate_up ... biggest remaining ~2x decode win"), and
the D7 numerical cross-check (SILOTIGER-667-plan-bench.md) could only validate gate_up_fp4 as
INFORMATIONAL: CK's gate_up FP4 runs the SLOW packed *scalar* path (dot2/NPerWarp=2 reject
packed FP4) whose tiled make_naive_tensor_view weight layout is swizzled -> value-set matches
(value_set_cos ~0.99) but output positions are permuted. down_fp4_h2 already has the fast path
and validates exactly (cos 0.999999), so it is the drop-in template.
Est ~1.5-2 days for a correct first cut; ~3-5 days for correct + competitive (~2x), the
tuning tail being the variable part. Anchor template = the down FP4 dot2 fast path in
projects/composablekernel/include/ck_tile/ops/warp_decode/kernel/warp_decode_down_reduce_kernel.hpp
(is_packed_w && kUseDot2 branches, 1-output and kHPerWarp==2/H2).
    Sub-steps:
    - Add a gate_up packed+dot2 branch mirroring down-H2: raw 128-bit packed loads
      (__builtin_memcpy, NOT load_tile) so a lane owns kVector contiguous FP4 along HIDDEN;
      fp4x2_to_bf16x2 + dot2_bf16_packed_raw_nonop into TWO accumulator sets (gate = x.wg,
      up = x.wu) sharing one loaded activation x (the down-H2 "two rows, one shared
      activation" structure); one dot2 drain; reuse the existing silu(gate)*up epilogue.
      Bonus: raw-load natural ordering fixes the swizzled output layout, so the result plugs
      straight into the D7 validator as a GATED cos~0.999999 cell. Est ~1-1.5 d.
    - Relax IsSupportedArgument (warp_decode_gate_up_kernel.hpp): currently rejects
      NPerWarp=2 && kUseDot2 && pk_fp4_t, and the dot2 body has static_assert(!is_packed_w).
      Carve out the new legal packed+dot2 gate_up config + add divisibility asserts
      (HIDDEN % (warp_size*kVector), etc.). Est ~0.5 d.
    - Wire type aliases / bench / dispatch / autotune: kVector 8/16/32 variants (8 = FP4 fast
      lane chunk, 32 = wide single-transaction), hook into ck_bench_warp_decode.cpp and the
      FlyDSL/AITER dispatch. Est ~0.5 d.
    - Correctness gate ("gate on accuracy", per ticket): validate via the D7 harness
      (tickets/667/harness: CK_WD_VALIDATE + validate.py). Once natural-ordered, move
      gate_up_fp4 from informational to a gated cos cell; watch silu sensitivity near 0. ~0.5 d.
    - Perf tune to actually hit ~2x (THE VARIABLE PART): accumulator count (4 vs 8), enough
      in-flight packed loads per wave (the H2 "double the loads" lever), possibly the
      software-pipelined prefetch already listed for down B=1. ~1-2 d.
    - OPTIONAL / decide up front: offline FP4 weight prepack + versioned layout contract
      (K3 report technique; ticket notes it is cheapest to introduce alongside FP4 gate_up
      rather than retrofit). Adds ~1-2 d + a layout-contract decision; a first fast path can
      ship without it (like down did).
    Cross-refs: SILOTIGER-667.md "Remaining/untried" #1 + "Datatypes targeted"
    ("MXFP4 only on the slow scalar path so far"); D7 note + B1 (1,32)-scale correction in
    SILOTIGER-667-plan-bench.md.
- REVISIT: once the fast path lands, the ticket's line-99 "refreshed head-to-head with

=== FlyDSL FP8-down block2d scaled-convert fold track (aiter kernel work; surfaced by the g9 caveat) ===
This track attacks the FP8-down block2d(128,128) cost that the g9_compare.md header flags as a
CK-favored lower bound ("block2d(128,128) costs FlyDSL ~10-38% vs pertensor (B1)"). The cost is
NOT weight-byte traffic (FP8-down fly_%peak is still ~66-74%); it is LATENCY: in the block2d branch
of build_down_reduce_fp8 (aiter/ops/flydsl/kernels/warp_decode_moe.py, the `if const_expr(block2d)`
path) the dot2 chain is drained PER 128-wide K-block so the per-block f32 scale can be folded after
the dot (`acc[h] += dot_i * (rw * ds_i)`), plus an extra scale buffer_load + address compute per
block -- vs the pertensor path which loads one broadcast scale and drains the whole K-range ONCE.
Fragmenting the dot2 ILP + the per-block drains is what hurts, worst at B=1 (the 38% end); it washes
out by B=32 (bandwidth-bound, FP8-down ratios already ~0.95-1.00). This is an implementation artifact,
not intrinsic to block scaling, so it is recoverable WITHOUT dropping to coarser pertensor scales
(which would be a model-accuracy decision, not a kernel win). Est ~1-1.5 days for the fold; +0.5-1 d
if the independent-partials variant is also needed. Anchor = the identity-scale convert today:
`fp8x2_to_bf16x2(dw[h][w_word], one_f32, hi=w_hi)` feeds a post-dot multiply by ds_i.
    Sub-steps:
    - Fold the per-block exponent into the scaled FP8->BF16 convert instead of the post-dot
      multiply: pass the block scale into v_cvt_scalef32_pk_bf16_fp8 (currently run with one_f32)
      so no separate per-block multiply is needed and the dot chain need not break to fold it.
      block scale is exponent-only, so this is a cheap swap of the convert's scale operand keyed on
      col_blk = k_base // scale_bk. Est ~1 d.
    - If the convert-fold alone does not restore ILP, keep independent per-K-block f32 partials in
      flight (extend the G7 dot2_acc idea ACROSS block boundaries) and fold each block's scale at the
      very end, rather than draining inside each block. Est ~0.5-1 d.
    - Correctness gate: reuse the existing block2d unit tests (h*_block2d / down_*_block2d cases in
      op_tests/flydsl_tests/test_flydsl_warp_decode_moe.py) at cos>=0.999; block2d output must be
      bit-comparable to the current fold (exponent-only scale is associative-safe here).
    - Perf-confirm at B=1/2 (the latency regime where the 10-38% lives) that FP8-down closes toward
      the pertensor number while keeping block2d(128,128); B>=8 is expected near-neutral (already at
      the memory wall). Re-run the G9 compare so the FP8-down cells reflect the recovered path.
    Cross-refs: g9_compare.md config-policy header ("FP8-down ratio is a CK-favored lower bound:
    block2d(128,128) costs FlyDSL ~10-38% vs pertensor (B1)"); SILOTIGER-667.md line 154 (K3 report:
    push dequant into the packed scaled-convert -- "the difference between a regression and a win");
    B1 scale note in SILOTIGER-667-plan-bench.md.
