=== Full-MoE / AITER track (complementary to the per-stage FlyDSL-vs-CK G9 plan) ===
This track answers "how does FlyDSL compare vs whatever AITER dispatches by default",
at the FULL fused-MoE level (routing + gate_up + activation + down), distinct from the
per-stage cold FlyDSL-vs-CK comparison. Anchor = the existing reference script
/workspaces/rocm-libraries/bench/bench_moe_warp_decode.py.
- extend bench_moe_warp_decode.py with FlyDSL paths.
    Context: that script already does the expensive full-MoE plumbing -- builds shared
    weights, prepacks into BOTH the AITER fused layout (shuffle_weight (16,16), w1/w2
    concat, 128x128 block quant) and the warp-decode flat scale layout, runs
    fused_topk + aiter.fused_moe (the DEFAULT dispatch, QuantType.per_1x128), a
    warp_decode_ext (bartified reference) FP8/BF16 path, a torch_moe_blockscale
    reference + correctness (cos/err), per-stage timings, GB/s, ratio, CSV. So we ADD
    FlyDSL as another path rather than build a harness. Est ~1-2 days (mostly wrappers +
    scale/signature reconcile + env), vs ~4-6 to build from scratch.
    Sub-steps:
    - Add FlyDSL path wrappers mirroring wd_bf16_moe_block / down, calling the registered
      aiter.ops.flydsl entries. Op mapping:
        wd_bf16 gate_up (BF16 act x FP8 w) <-> flydsl_warp_decode_gate_up (block2d).
        down <-> flydsl_warp_decode_down_reduce (block2d).
        FP4 gate_up/down (flydsl_..._fp4) -> NEW columns the script lacks.
        wd_fp8 gate_up is FP8-ACTIVATION x FP8-w -> FlyDSL has no peer yet; BLOCKED on the
          "FlyDSL counterpart to gate_fp8_d2" item (step B4 in SILOTIGER-667-plan-bench.md).
    - Reconcile signatures + scale layout: FlyDSL uses w_scale_mode="block2d",
      scale_block=(128,128), out=; verify the script's w_*_scale_wd ([E*N/128, K/128])
      matches FlyDSL's block2d expectation; confirm router_ids i32 / router_wts f32.
    - Reconcile the environment (MAIN RISK): the script imports a locally-built
      warp_decode_ext in the default env; FlyDSL needs flydsl_venv (triton 3.6). Need ONE
      env with aiter+fused_moe + warp_decode_ext + flydsl importable together.
    - Result is a 3-(or-4-)way table: AITER default vs warp_decode_ext (ref) vs FlyDSL
      (+ CK if later merged); reuse default-vs-default config policy + provenance/variance.
- REVISIT: warm-ish cold semantics of bench_moe_warp_decode.py (don't forget).
    The script builds weights once per shape and reuses them across B/iters with a fixed
    router (fused_topk on random gating) and run_perftest's default rotation -> selected
    experts stay MALL-resident where they fit == WARM-ish, same caveat as CK's default
    (before "flip CK to cold"). For decode realism the weight reads should be COLD.
    Possibly worth revisiting: apply the same treatment as the FlyDSL cold harness
    (oversized pool + router rotation over disjoint expert groups, or a cache flush) so
    the full-MoE numbers are cold too; at minimum, label the regime in the output.
